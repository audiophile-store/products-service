# Change history

## 2026-10-02

- Added `--env-file=.env` to the development script so the application can read local configuration through `process.env`, without an additional package.
- Kept the production start script unchanged so Render can supply environment variables directly.
- Documented local environment loading and the minimum Node.js version in the README.
- Added an exported PostgreSQL pool in `src/db.ts`, using `DATABASE_URL` and the default maximum of 10 connections. Missing configuration fails explicitly, and idle connection errors are logged.
- The pool is not yet imported by the server; routes will use it when database queries are added.
- Declared the package as an ECMAScript module to match the existing import/export syntax and TypeScript `nodenext` configuration.
- Configured TypeScript to compile only `src` into `dist`, matching the production start command, and documented the build workflow.
- Added a negative-price integration test in `tests/products.test.ts`. It requires PostgreSQL error `23514` from the planned `products_price_nonnegative` constraint, so unrelated failures cannot count as a successful rejection. The test checks the database name and rolls back its transaction.
- Added a duplicate-ID integration test: the first insert must succeed, and the second must fail with PostgreSQL error `23505` from `products_pkey`. Both inserts run in a rolled-back transaction to keep the test database clean.
- Added checks for `NULL` in all 12 required fields, empty and space-only values in the five required text fields, and negative stock. A shared rejection helper keeps these cases consistent; assertions require the specific PostgreSQL error and column or constraint, with database-name guards and transaction rollback.
- Added `migrations/001_create_products.sql` with the agreed required fields, JSONB columns, exact EUR prices, primary key, and named checks. The user applied it to the test and development databases and reported all 26 table tests passing.
- Added three seed integration tests for the planned `seedProducts(client, products)` function: preserving all fields of a synthetic 13-product catalog, rejecting repeated seeding without overwriting existing data, and rolling back a late invalid product without losing pre-existing data. Tests use temporary tables copied from the migrated schema so seed commits cannot leave persistent test rows. The seed implementation is intentionally not written yet.
- Implemented `seedProducts` in `src/seed.ts` after the user confirmed all three seed tests failed because the module was missing. It maps catalog fields to SQL columns, uses parameterized inserts in one transaction, rejects duplicate IDs, and propagates errors after rollback. Importing the module does not connect to a database or seed data; loading the real catalog and a command-line entry point remain separate steps.
- Verified the seed implementation: all 29 schema and seed tests pass, and the TypeScript build succeeds. No real catalog was inserted into the development database.
- Added four catalog-loading tests for the planned `loadCatalog(path)` function: preserving valid data, reporting missing files, rejecting malformed JSON, and rejecting invalid catalog or product structures with a clear error. Temporary fixture files are cleaned up automatically; no database is used, and the loader and seed command are not implemented yet.
- Implemented `loadCatalog` in `src/catalog.ts` after the user confirmed the missing-module failures. It reads UTF-8 JSON, validates required product fields and nested data without unchecked casts, and preserves valid catalog values. File and JSON parsing errors propagate, while invalid structures raise a descriptive `TypeError`; this module does not connect to the database.
- Verified catalog loading together with the existing database tests: all 33 tests pass and the TypeScript build succeeds. The real catalog has not been copied or inserted yet.

Documented migration prerequisites and duplicate-ID behavior in the README. The development database has not been seeded.

Tests expect a separate `createApp(client)` factory, use ephemeral HTTP ports and temporary tables in `products_test`, and close connections and servers. API implementation has not been written yet.
